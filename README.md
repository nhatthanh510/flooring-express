# Flooring Express Hobart

Marketing site for a Hobart flooring installation business — Hybrid, Laminate and Timber.

Built from the [Stitch design](https://stitch.withgoogle.com/projects/4391856311392807811); the **Timber & Slate** design system is documented in [`DESIGN.md`](./DESIGN.md).

**All content lives in Sanity.** Copy, imagery and business details are edited
in the Studio embedded at [`/studio`](http://localhost:3000/studio); nothing
editorial is hardcoded. The quote form is still a stub — it validates
client-side and shows a simulated success state.

## Stack

Next.js 16 (App Router) · React 19 · TypeScript · Tailwind CSS v4 · shadcn/ui
(radix base) · react-hook-form + zod · lucide-react · Sanity (next-sanity)

## Getting started

```bash
pnpm install
cp .env.example .env.local   # fill in the Sanity project id and tokens
pnpm dev        # http://localhost:3000 — Studio at /studio
pnpm build      # production build
pnpm lint
pnpm typecheck
pnpm typegen    # regenerate src/sanity/types.ts after a schema or query change
```

`pnpm typegen` must be re-run whenever a schema in `src/sanity/schemaTypes/` or
a query in `src/sanity/queries.ts` changes — the generated types are what the
components are written against, so a stale file shows up as a type error rather
than a runtime surprise.

## Content

| | |
| --- | --- |
| Studio | `/studio` — embedded, so one repo and one deploy |
| Schemas | `src/sanity/schemaTypes/` — objects, documents, singletons |
| Queries | `src/sanity/queries.ts` — every GROQ query, all `defineQuery` |
| Types | `src/sanity/types.ts` — **generated**, do not edit |
| Fetching | `sanityFetch` from `src/sanity/lib/live.ts` |

Six document types (flooring services, gallery projects, case studies, FAQs,
FAQ categories, process steps) plus seven singletons (site settings and one per
page). Editors reach them through the desk structure in `src/sanity/structure.ts`.

Content updates reach the site through Sanity's Live Content API: `<SanityLive />`
in the marketing layout revalidates exactly the pages that read a changed
document. No webhook is required.

### Previewing drafts

Open Presentation in the Studio. It calls `/api/draft-mode/enable`, which
validates a single-use secret before turning on Next's draft mode; from there
unpublished content renders and click-to-edit overlays appear. The banner at the
foot of the page exits preview via a POST — not a link, because Next would
prefetch it and clear the cookie.

**One manual step per environment:** add the site's origin as a CORS origin in
[sanity.io/manage](https://sanity.io/manage) → API → CORS origins
(`http://localhost:3000` for development, plus each deployed URL), with
credentials allowed. Without it the Studio loads but cannot query.

## Design tokens

`src/app/globals.css` is the single source of truth. `:root` maps `DESIGN.md`
onto shadcn's semantic variables (`--primary`, `--secondary`, `--muted`, …); the
`@theme` block adds the brand scales that compile to utilities:

| Utility | Example |
| --- | --- |
| Brand colours | `bg-ink`, `text-oak`, `bg-sand`, `border-hairline`, `bg-surface-low` |
| Type scale | `text-display-lg`, `text-headline-lg`, `text-body-md`, `text-label-sm` |
| Layout | `py-section` (80px), `gap-gutter` (24px), `max-w-page` (1280px) |
| Elevation | `shadow-ambient`, `shadow-ambient-lifted` |
| Helpers | `.container-page`, `.glass-panel`, `.zebra-rows` |

The site is light-mode only — `DESIGN.md` defines no dark palette. Because every
component uses semantic tokens, adding one later means adding a `.dark` block,
not touching components.

## Before launch

1. **Replace the placeholder contact details** in the Studio, under Site
   settings. The mockups disagreed with each other on the email domain, phone
   format and closing time; the migrated values are the most common variant of
   each, not confirmed business data. Note that `openingHoursSpec` (the
   schema.org field search engines read) has to be updated alongside the hours
   table — they are two separate fields by design, because the display strings
   are free text.
2. **Wire up the quote form.** `submitQuote()` in `src/lib/submit-quote.ts`
   currently resolves after a delay. Swap its body for the real API/CRM call —
   nothing else needs to change.
3. **Set `NEXT_PUBLIC_SITE_URL`** (see `.env.example`) — or deploy to Vercel,
   where it is detected automatically. See "Why a shared link has no image".
4. **Replace the imagery.** The migrated assets are the AI-generated
   placeholders from the Stitch mockup (~1376×768 WebP), now on Sanity's CDN.
   Swap them in the Studio — no deploy needed. Alt text travelled with each
   image and should be re-checked against the real photos. `public/images/` is
   no longer read by the app and can be deleted once the real photos are in.
5. **Privacy Policy / Terms of Service** pages from the mockup footer aren't
   built — the Quick Links column points at pages that exist instead.
6. **Add the production URL as a Sanity CORS origin**, and create a separate
   read token per environment rather than sharing one.

## Where CTAs go

Every call to action carries an **enquiry intent**, so no two buttons land on an
identical form. `/contact` reads `?enquiry=` and `?flooring=` and adapts its
heading, description, submit label and preselected options
(`enquiryCopy` in `lib/schemas/quote.ts`). The four intents are `quote`,
`consultation`, `samples` and `commercial`, matching the "Inquiry Type" field in
the updated contact mockup. The regression suite asserts that no page has two
CTAs pointing at the same contact URL.

The mockup's fourth option is "General Inquiry"; we use **Commercial Project**
instead, because the gallery's "Contact Sales" CTA needs a distinct destination
and a commercial lead is worth routing separately.

## Notes

- `/gallery` is server-rendered on demand because it reads `?category=`; the
  filter pills are real links, so filtered views are shareable, crawlable, and
  work without JavaScript. Every other route is statically prerendered — the
  three case studies via `generateStaticParams`.
- Icons are `lucide-react` components, mapped from the Material Symbols used in
  the mockups.
- `pnpm screenshots` (dev server running) captures every route at 1440px and
  390px into `screenshots/`, and reports horizontal overflow, console errors and
  failed requests. Override with `BASE=`, `ROUTES=`, `OUT=`.
- `pnpm perf-audit` reports LCP / CLS / TTFB and per-route byte weight against a
  production build (`pnpm build && pnpm start --port 3222`, then
  `BASE=http://localhost:3222 pnpm perf-audit`).
- `pnpm mobile-audit` checks every route at 390px for horizontal overflow,
  elements escaping the viewport, tap targets under 32px, and clipped text.
- `pnpm regression` runs the functional suite — link integrity, gallery filters
  and card links, quote-form validation and success, the plank toggle, mobile
  nav, footer structure, CTA intent routing, control overflow at four widths,
  and that card hover stays on the compositor.
- **The contact map is the only third-party resource.** Google's embed pulls
  ~1.6 MB of JavaScript — more than the rest of the site combined — so `/contact`
  is by far the heaviest route. It is lazy-loaded, so it only downloads once the
  map scrolls into view. If that cost ever matters, `ServiceAreaMap` is the one
  file to change (a click-to-load facade cuts it to zero). Everything else is
  same-origin; the Facebook icon is an outbound link, not a load.

## SEO & sharing

- Per-route **Open Graph / Twitter cards** generated at build time by
  `next/og` from `src/app/og.tsx` — each route re-exports it with its own title,
  so a shared link previews what was actually shared. Case studies generate one
  per project.
- **Favicon and apple-touch-icon** are generated the same way (`app/icon.tsx`,
  `app/apple-icon.tsx`), so they can't drift from the palette.
- `manifest.webmanifest`, canonical URLs on every route, `robots` directives with
  `max-image-preview:large`, and `geo.region` / `geo.placename` for local search.
- Structured data: `HomeAndConstructionBusiness` site-wide, `FAQPage` on `/faq`.

### Why a shared link has no image

Social crawlers fetch `og:image` as an **absolute** URL. If that URL points at a
host which isn't serving the site, the preview degrades to title + description
with no image — which is exactly what happens when `metadataBase` is hard-coded
to a domain that isn't live yet.

`siteConfig.url` therefore resolves at runtime, in this order:

1. `NEXT_PUBLIC_SITE_URL` — set this when self-hosting, or when testing shares
   through a tunnel (ngrok, cloudflared).
2. Vercel's production/preview URL, so preview deployments preview correctly.
3. The production domain.

Note that **a `localhost` link can never produce a preview**, whatever the tags
say — the crawler cannot reach your machine. To test a real share, expose the
site with a tunnel and set `NEXT_PUBLIC_SITE_URL` to the tunnel origin.

### Typography

Per `DESIGN.md`, **Montserrat is for the display/headline scale only; Inter is
for body and UI text.** Most page text is body text, so Inter is what you'll see
most of the time — that is the design, not a loading failure. In DevTools the
computed stack reads `Inter, "Inter Fallback"`; `"Inter Fallback"` is `next/font`'s
metric-matched local fallback and always sits second in the stack. Check the
"Rendered Fonts" section instead to see what actually painted.

If you want Montserrat as the base font for everything (the Stitch
implementation guide suggests `sans: Montserrat`, contradicting `DESIGN.md`),
change `--font-sans` in `globals.css` to `var(--font-montserrat)` and add the
lighter Montserrat weights to the `next/font` call in `app/layout.tsx`.

### Where mockups disagree

Stitch generated the desktop and mobile screens independently, so they conflict
in places. The rule applied throughout: **desktop wins on copy, mobile wins on
layout mechanics.** Concretely, the mobile screens' alternative hero wording,
white hero buttons and dropped section eyebrows were not adopted; their
centred mobile alignment, 28px mobile headings and full-width stacked buttons
were. Contact details differ between screens too — see "Before launch" above.
